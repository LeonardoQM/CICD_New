# CI/CD Pipeline — Hello App

This repository contains a simple **CI/CD pipeline implemented with GitHub Actions** to automatically test, containerize, publish, and update the Kubernetes deployment of a Dockerized application.

The pipeline is triggered automatically whenever changes are pushed to the `main` branch.

## Pipeline Overview

The workflow performs the following steps:

```text
Git Push to main
       │
       ▼
Checkout Repository
       │
       ▼
Generate Docker Image Tag
       │
       ▼
Install pytest
       │
       ▼
Run Automated Tests
       │
       ├── FAIL ──► Pipeline stops
       │
       ▼
Build Docker Image
       │
       ▼
Login to Docker Hub
       │
       ▼
Push Docker Image
       │
       ▼
Update Kubernetes Deployment
       │
       ▼
Verify deployment.yaml
       │
       ▼
Commit deployment change
       │
       ▼
Push change to GitHub
```

## GitHub Actions Workflow

The workflow is defined in:

```text
.github/workflows/CICD_New.yml
```

It runs on:

```yaml
on:
  push:
    branches:
      - main
```

Therefore, every push to `main` automatically starts the CI/CD process.

## 1. Checkout the Repository

The workflow first checks out the source code using the official GitHub Actions checkout action:

```yaml
- name: Checkout repository
  uses: actions/checkout@v4
```

This makes the application source code and Kubernetes manifests available to the GitHub Actions runner.

## 2. Generate an Image Tag

The Docker image is tagged using the first seven characters of the Git commit SHA:

```bash
IMAGE_TAG=${GITHUB_SHA::7}
```

For example:

```text
a81f3c2
```

The resulting Docker image could therefore be:

```text
leonardoq/hello-app:a81f3c2
```

Using the commit SHA provides a simple and traceable relationship between a Docker image and the source code version that produced it.

## 3. Install and Run Tests

The pipeline installs `pytest`:

```bash
pip install pytest
```

and executes the application's automated tests:

```bash
pytest
```

Testing happens **before the Docker image is built and published**.

If the tests fail, the GitHub Actions job stops and the image is not pushed to Docker Hub.

This provides a basic CI quality gate.

## 4. Build the Docker Image

After the tests pass, the application is containerized:

```bash
docker build -t leonardoq/hello-app:${IMAGE_TAG} .
```

The resulting image is tagged with the Git commit identifier.

Example:

```text
leonardoq/hello-app:a81f3c2
```

## 5. Authenticate with Docker Hub

The workflow authenticates against Docker Hub using GitHub Actions secrets:

```yaml
username: ${{ secrets.DOCKER_USERNAME }}
password: ${{ secrets.DOCKER_PASSWORD }}
```

The credentials are not stored directly in the workflow.

The repository therefore requires the following GitHub repository secrets:

```text
DOCKER_USERNAME
DOCKER_PASSWORD
```

## 6. Push the Image to Docker Hub

Once authenticated, the image is published:

```bash
docker push leonardoq/hello-app:${IMAGE_TAG}
```

The Docker image is now available in the configured Docker Hub repository.

## 7. Update the Kubernetes Deployment

The pipeline automatically updates the image reference in:

```text
k8s/deployment.yaml
```

using:

```bash
sed -i "s|image: leonardoq/hello-app:.*|image: leonardoq/hello-app:${IMAGE_TAG}|g" k8s/deployment.yaml
```

For example, an existing deployment:

```yaml
image: leonardoq/hello-app:oldtag
```

is changed to:

```yaml
image: leonardoq/hello-app:a81f3c2
```

This keeps the Kubernetes manifest synchronized with the Docker image generated by the pipeline.

## 8. Verify the Kubernetes Manifest

The modified deployment file is printed to the workflow log:

```bash
cat k8s/deployment.yaml
```

This provides a simple verification mechanism and makes the resulting image version visible in the GitHub Actions execution log.

## 9. Commit the Deployment Change

The workflow configures Git using the GitHub Actions bot identity:

```bash
git config --global user.name "github-actions[bot]"
git config --global user.email "41898282+github-actions[bot]@users.noreply.github.com"
```

It then commits the updated Kubernetes manifest:

```bash
git add k8s/deployment.yaml
git commit -m "Update image to ${IMAGE_TAG} [skip ci]"
```

The `[skip ci]` marker prevents the automatically generated commit from triggering another CI/CD execution.

If there are no changes to commit, the workflow continues:

```bash
|| echo "No changes to commit"
```

## 10. Push the Updated Manifest

Finally, the workflow pushes the modified Kubernetes deployment back to the repository:

```bash
git push
```

The Git repository therefore contains the exact Docker image version that corresponds to the latest successful pipeline execution.

## CI/CD Responsibilities

The pipeline combines several common DevOps practices:

| Stage           | Responsibility                                  |
| --------------- | ----------------------------------------------- |
| GitHub Actions  | Pipeline orchestration                          |
| pytest          | Automated testing                               |
| Docker          | Application containerization                    |
| Docker Hub      | Container image registry                        |
| Kubernetes YAML | Deployment configuration                        |
| Git             | Version control and deployment manifest history |

## Deployment Model

This pipeline follows a simple **build-and-update-manifest** model:

1. Developer pushes code to `main`.
2. GitHub Actions runs automated tests.
3. A Docker image is built only if tests pass.
4. The image is tagged with the Git commit SHA.
5. The image is pushed to Docker Hub.
6. The Kubernetes deployment is updated with the new image tag.
7. The updated deployment manifest is committed back to Git.

The actual Kubernetes deployment is intentionally separate from this workflow. A Kubernetes cluster or GitOps controller can consume the updated manifest and perform the deployment.

## Why Use the Git Commit SHA as the Image Tag?

Using a commit-based tag provides traceability:

```text
Git commit
    │
    ├── Docker image
    │       └── leonardoq/hello-app:a81f3c2
    │
    └── Kubernetes deployment
            └── image: leonardoq/hello-app:a81f3c2
```

This makes it possible to determine which source-code revision produced a particular container image.

It also avoids relying exclusively on mutable tags such as:

```text
latest
```

## Required Repository Secrets

The workflow expects the following GitHub repository secrets:

```text
DOCKER_USERNAME
DOCKER_PASSWORD
```

These credentials are used exclusively by the GitHub Actions workflow to authenticate with Docker Hub.

## Example Result

After a successful execution, the repository might contain:

```yaml
containers:
  - name: hello-app
    image: leonardoq/hello-app:a81f3c2
```

while Docker Hub contains:

```text
leonardoq/hello-app:a81f3c2
```

The same version identifier therefore connects the **source code, container image, and Kubernetes deployment configuration**.

## Summary

This project demonstrates a lightweight CI/CD implementation using GitHub Actions:

**Test → Build → Publish → Update Kubernetes Manifest → Commit**

It provides a practical example of integrating automated testing, containerization, image versioning, container registry publishing, and Kubernetes deployment configuration into a single automated workflow.
